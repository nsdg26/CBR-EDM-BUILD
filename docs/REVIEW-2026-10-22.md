# Code review: vulnerabilities, bugs and improvements (22 Oct 2026)

Scope: every file under `src/`, `public/js/`, `public/sw.js`, `migrations/`,
`wrangler.jsonc`, the README and SPEC section 12. Reviewed on `main` at
commit 656ada2. Test suite: 237 tests, all passing once `npm ci` has run
(the one failure seen before that was only the missing `postal-mime` package).

Status (same branch, later commit): every item below is fixed in code
except S10, which is a git history rewrite and the owner's call; S1 and
S3 also ask for a dashboard setting (README step 10) and a secret rotation
that only the owner can do. Tests for the fixes are in
`test/reviewFixes.test.js`. Line numbers below refer to the code as it
was when reviewed.

## Security

### S1. Admin actions can be forged cross-site (CSRF) - high

- Every admin write is a plain HTML form POST with no CSRF token and no
  Origin or Sec-Fetch-Site check (`src/routes/admin/router.js:33` onwards).
- Cloudflare Access sets the `CF_Authorization` cookie with
  `SameSite=None` by default (Cloudflare docs, "Authorization cookie").
  A page on any other site can therefore submit a hidden form to, for
  example, `/admin/events/<id>/delete` or `/admin/crews/<id>/issue-key`
  while the admin is signed in, and the browser will send the cookie.
  Access accepts it, adds the JWT header, and the Worker performs the
  action. Delete is a hard delete.
- Fix: in `adminRouter`, reject any non-GET/HEAD request whose
  `Sec-Fetch-Site` header is not `same-origin`/`none`, or whose `Origin`
  header does not match the request's own origin (or the admin host). Two
  lines, no template changes. Independently, set the Access application's
  SameSite attribute to Lax or Strict in the Zero Trust dashboard.

### S2. The dev auth bypass is only guarded by one variable - medium

- `src/lib/auth.js:126`: if `DEV_BYPASS_ACCESS` is ever `"true"` in a
  deployed Worker (a stray dashboard variable, a copied `.dev.vars` into
  `vars`), the whole admin is open with no sign-in.
- Fix: also require the request hostname to be `localhost`, `127.0.0.1`
  or `*.localhost` before honouring it.

### S3. Rate-limit salt is still the placeholder - medium

- `wrangler.jsonc:45` ships `RATE_LIMIT_SALT: "REPLACE_WITH_A_RANDOM_STRING"`.
  The hashing in `src/lib/rateLimit.js` is meant to stop the database
  holding reversible IP addresses. With a known salt and a known day key,
  the whole IPv4 space can be hashed in minutes, so the rate_limits rows
  are reversible to IPs if the database is ever exported or leaked.
- Fix: set a random value (as a secret, not a var), as the comment in the
  file already asks for.

### S4. Email sender address is written into a public field - medium

- `src/routes/admin/inboundEmails.js:76` writes
  "Converted from an email sent by <address>" into `notes`. `notes` is
  rendered on the public event page once the event is published
  (`src/templates/eventPage.js`). SPEC section 12 says submitter
  contact details are never exposed publicly. An admin who converts an
  email and publishes without clearing that line publishes the sender's
  email address.
- Fix: put the sender into `submitter_contact` (private, already shown on
  the admin form) and leave `notes` empty.

### S5. Content Security Policy is missing three directives - low

- `src/lib/securityHeaders.js`: no `base-uri`, `object-src` or
  `form-action`. Add `base-uri 'self'; object-src 'none'; form-action 'self'`.
  Also consider `Strict-Transport-Security` (or turn HSTS on at the zone).

### S6. The edit and crew pages do not get `no-referrer` - low

- SPEC section 12 asks for `Referrer-Policy: no-referrer` on `/edit` and
  `/crew`. `src/routes/edit.js:13` sets it, but `withSecurityHeaders`
  (`src/lib/securityHeaders.js:38`) overwrites it on every HTML response
  because `src/index.js` always passes `{}`. `/crew` never sets it at all.
  Impact is small because the token lives in the URL fragment, which is
  never sent as a referrer, but the stated policy is not in effect.
- Fix: in `withSecurityHeaders`, only set Referrer-Policy when the
  response has not already set one.

### S7. Smaller auth hardening - low

- `src/lib/auth.js:69` checks the issuer with `includes(teamDomain)`.
  Compare against the exact `https://<team domain>` string.
- `src/lib/auth.js:84` refetches the JWKS whenever a token carries an
  unknown `kid`. On a hostname Access does not front (see S8) an
  attacker can force one certs fetch per request. Add a cooldown (for
  example, no more than one refresh per minute).
- No `nbf`/`iat` check; harmless today but cheap to add.

### S8. Make sure the workers.dev hostname is off - low

- `wrangler.jsonc` does not set `"workers_dev": false` or
  `"preview_urls": false`. If the default `*.workers.dev` route is live,
  the public site is duplicated on a hostname Access does not protect.
  The Worker's own JWT check still blocks `/admin` there (good), but the
  rest of the site, Turnstile hostname rules and SEO are affected.
- Fix: add both settings (or confirm they are off in the dashboard).

### S9. Turnstile key comment is wrong - informational

- `wrangler.jsonc:40` says the site key is Cloudflare's "always passes"
  test key, but `0x4AAAA...` is the format of a real site key (the test
  key is `1x00000000000000000000AA`). Either the comment is stale or the
  key is. Confirm the production `TURNSTILE_SECRET_KEY` secret is the real
  one: the test secret in `.dev.vars.example` accepts any token.

### S10. Personal email in git history - informational

- Two commits on `main` are authored with a personal Gmail address
  (`git log --format='%ae'`). SPEC section 12 and README step 1 ask for
  the GitHub noreply address. Rewriting history is your call; at minimum
  set `git config user.email` on the desktop clones.

## Bugs

### B1. Crews lock themselves out of the dashboard - medium

- `public/js/crew-dashboard.js:193` re-checks the stored key against
  `/api/crew/login` on every page load. `src/routes/crew.js:51` counts
  every call in the `crew_key` bucket, limit 10 per IP per day, before
  it even looks at the key. Opening the dashboard ten times in a day
  (or two people behind one NAT) locks that IP out until the next
  Canberra day, including the crew-key path on the public submit form
  (`src/routes/submit.js:68`, same bucket).
- Fix: only count failed attempts (increment after the lookup misses),
  or give the "re-check a stored key" path its own, much higher limit.

### B2. Analytics writes can take the public site down - medium

- Every public page does `await recordCount(...)` with no try/catch
  (`src/routes/home.js`, `event.js`, `calendar.js`, `calendarFeed.js`,
  `go.js`). A D1 write failure, including hitting the free tier's
  100,000 writes per day under a crawler that does not say "bot" in its
  User-Agent, turns every home and event page into a 500.
- `src/index.js:11` also drops the `ctx` argument, so the write cannot be
  moved off the response path with `ctx.waitUntil`.
- Fix: accept `ctx`, run `recordCount` inside `ctx.waitUntil` wrapped in
  try/catch, and never let it block or fail the page.

### B3. Venue check fails closed on third-party outages - medium

- `src/lib/geocode.js:71` returns `null` for any failure: a timeout, a
  5xx or a Nominatim ban look identical to "address not found".
  `src/routes/submit.js` and `edit.js` then reject the submission with
  "we couldn't find that venue". So an outage or a rate-limit ban at a
  community-run service blocks every public submission that has a venue.
  The public `/api/venue-check` endpoint (40 per IP per day) also lets
  strangers push the site past Nominatim's one request per second policy,
  which is how such a ban would happen.
- Fix: distinguish "service unavailable" (fail open, let the submission
  through, flag it for the admin) from "no result" (fail closed as now).
  Consider a small per-minute global cap on geocoder calls.

### B4. An approved edit or trusted crew edit can blank a live event - low

- `src/routes/admin/changes.js:63` writes every proposed field, including
  a null `title` or `start_at`, onto a published event. A trusted crew's
  direct update does the same (`src/routes/crew.js`, `handleCrewEventUpdate`).
  `handleEventPublish` requires both fields, but nothing re-checks after
  publication. A published event with no `start_at` is never "past", so
  it sits at the top of "Coming up" with no date forever.
- Fix: when the target event is published, refuse (or send to review) a
  change that empties `title` or `start_at`.

### B5. Admin forms skip validation and 500 on bad values - low

- `src/routes/admin/events.js:81` and `:114` call `readEventFields` but
  never `validateEventFields`. A `status` or `age_restriction` outside the
  CHECK constraint, or an over-length field, fails inside D1 as a 500
  instead of an error message. Only an admin can trigger it, but a
  hand-edited form or a future UI change makes it easy to hit.
- `src/routes/admin/crews.js:31`: the slug is stored as typed. A
  duplicate slug 500s on the UNIQUE index; a slug containing `/` makes
  `/crews/:slug` unreachable; an empty name gives an empty slug.
- Fix: validate in both handlers and re-render the form with the error,
  the way `handleEventPublish` already does.

### B6. Slug collisions are possible and unhandled - low

- `src/lib/ids.js` adds a 4-hex suffix (65,536 values) to
  `title-date`. Two submissions with the same title on the same day
  collide with probability 1 in 65,536, and `src/routes/submit.js:78`
  then fails the INSERT as a 500 after Turnstile has been consumed.
- Fix: catch the UNIQUE failure and retry with a new suffix, or use 8
  hex characters.

### B7. Public JSON endpoints assume string fields - low

- `src/routes/crew.js` spreads the JSON body into `readEventFields`;
  `src/lib/eventFields.js` then calls `.trim()` on `ticket_url` and
  `src/routes/submit.js` (`handleVenueCheck`) calls `.slice` on
  `venue_name`. A number or object in those fields throws a TypeError and
  returns a bare 500. Coerce with `String()` or reject non-strings.

### B8. Admin "not found" pages are publicly cacheable - low

- `src/lib/http.js:16` sends `Cache-Control: public, max-age=60` and the
  public layout. The admin router uses it for a missing event or crew,
  so an admin 404 is marked cacheable and wears the public chrome. Give
  the admin its own `no-store` 404.

### B9. Build id replacement can hit user content - trivial

- `src/lib/securityHeaders.js` replaces the first `CF_VERSION_ID` in the
  whole HTML body. If a title or note contains that string, it gets the
  build id and the footer comment does not. Replace the full
  `<!-- build:CF_VERSION_ID -->` marker instead.

## Improvements

### I1. The home page loads and renders every published event ever

- `src/routes/home.js:19` selects every published row, elevation grids
  included, and `homePage` renders a flyer SVG for each one before
  keeping only 12 past events. As the archive grows this is more rows
  read and more CPU per request on a plan with a 10 ms CPU budget; the
  render memo only helps on a warm isolate. `src/routes/archive.js` does
  the same just to list years.
- Fix: in SQL, take upcoming rows plus the most recent N past rows (a
  `start_at >= now - 2 days` window covers the "past at 6am" rule, plus a
  `LIMIT 12` query for past). For the archive index, `SELECT DISTINCT`
  the year.

### I2. Add a top-level error handler

- `src/index.js` has no try/catch, so any thrown error is the runtime's
  bare "Internal Server Error". Wrap the router: log the error, return
  the styled page with a 500 status, keep the security headers.

### I3. Prune the two append-only tables

- `rate_limits` and `daily_counts` are never deleted from. A daily cron
  trigger (`triggers.crons` in `wrangler.jsonc`, `scheduled()` handler)
  that deletes rate_limits rows older than two days keeps the table tiny
  and removes the hashed-IP rows as soon as they are useless.

### I4. Verify Turnstile after cheap validation

- `src/routes/submit.js` and `contact.js` verify the single-use Turnstile
  token before field validation, so a "title too long" error burns the
  token and the visitor has to redo the check. Validate first, then
  verify Turnstile, then do the geocoder call.

### I5. Inbound email has no sender controls

- `src/lib/inboundEmail.js` stores up to three images (up to 10 MB each
  email) from any sender into R2 under `inbound/`, with no pruning and an
  admin alert email per message. Spam to `events@` fills R2 and the
  admin's inbox. Consider a size cap per attachment, a daily cap on
  stored emails, and deleting attachment objects when an email is
  dismissed or its event deleted.

### I6. Crew key brute force protection is inconsistent

- Only `/api/crew/login` and the submit form's key path are rate
  limited. `/api/crew/events/list` and every other crew endpoint look
  the key up with no limit. A 256-bit key cannot be guessed in practice,
  so this is tidiness rather than exposure, but one `requireCrew` with a
  failure-counting limit would make the rule uniform.

### I7. Small things

- `src/routes/crew.js`, `handleCrewFlyerPreview`: no length limits on the
  preview body, so a crew can send a huge lineup and burn CPU. Run
  `validateEventFields` first.
- `wrangler.jsonc`: `ACCESS_AUD` is a var although SPEC section 12 lists
  it as a secret. It is not sensitive; update the spec or move it.
- `src/routes/calendarFeed.js` and `event.js` build the `.ics` from the
  Host header via `new URL(request.url).host`. On Workers that host is
  the routed hostname, so this is fine; noting it only so nobody later
  trusts a forwarded header there.
